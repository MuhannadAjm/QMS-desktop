# Document Control & File Safety

Authoritative reference for how QMS Desktop stores, serves, protects and approves
controlled document files.

---

## 1. The filesystem trust model

The renderer is treated as untrusted. Not because it is expected to be hostile,
but because a command that accepts a path from it is a command whose safety
depends on every line of frontend code and every dependency in the bundle.

| Case | Who names the location | Rule |
|---|---|---|
| **A. Managed document storage** | The backend, from a database id | The caller sends a `document_id`. The filename comes from the database, the directory from `get_storage_paths`. No caller-supplied component is ever joined into a path. |
| **B. Import source** | The user, in a native dialog | Read-only, copied inward once. Validated as a real regular file. Nothing later writes to or deletes it. |
| **C. Export destination** | The user, in a native dialog opened **by the backend** | Written once, in the call that presented the dialog. The renderer never sees or supplies a path. |
| **D. Internal app files** | The backend | Confined to `%APPDATA%\QMSDesktop`. |

### `resolve_managed_file`

Every attachment operation resolves through it. Both the candidate and the
storage root are **canonicalised** and compared by resolved ancestry.

A string prefix check would be wrong on Windows: junctions and symlinks can share
a textual prefix while resolving elsewhere, and `..`, mixed separators, short
(8.3) names and case differences all defeat text matching. `canonicalize` reduces
all of those to one true form. The stored value is additionally rejected outright
if it is not a bare filename.

## 2. `write_text_file` — removed

It was the one genuinely dangerous command in the codebase:

```rust
#[tauri::command]
pub fn write_text_file(path: String, content: String) -> Result<(), String>
```

No `current_user_id`, no permission check, any absolute path, and `create_dir_all`
on the parent. The intended flow was safe — the frontend opened a save dialog and
passed the result through — but the backend could not tell an operator-chosen path
from a fabricated one. Anything able to invoke a command could overwrite any file
the Windows user could write, including `data.db` and `license.json`.

It was **alive**, not dead: `exportService.saveFile()` called it for CSV/JSON
export across all six registers and the Reports screen.

Adding a permission check would not have fixed it. With the path still arriving
from the renderer, an authorised user would simply have become an authorised
arbitrary-write. The replacement removes the capability instead of guarding it:

```rust
pub fn export_text_file(app, current_user_id, kind, suggested_name, extension, content)
    -> Result<Option<String>, String>
```

The save dialog is opened **in Rust**, and the file is written to the path the
human picked during that same call. The caller names a *register*, not a
permission — the backend maps `documents` / `capa` / `risks` / `complaints` /
`audits` / `nc` / `report` to the key it enforces, so a renderer cannot nominate
its own authorisation. `create_dir_all` is gone.

## 3. Storage model

```
%APPDATA%\QMSDesktop\uploads\documents\{document_id}_{unix_micros}.{ext}
```

The stored filename is **generated by the backend** — digits, an underscore and a
validated extension. No user-controlled component reaches it, which is why the
external-open path has no injection surface.

`documents.file_path` and `document_revisions.file_path` hold that bare filename,
never a path. Each attach writes a new revision row pointing at the new file, so
revision history references historical files and a removal must check for other
referents before deleting bytes.

## 4. Lifecycle

Three statuses already existed and are reused rather than duplicated:

| Status | Meaning | File may be changed? |
|---|---|---|
| `UNDER PROCESS` | Draft, or rejected and awaiting correction | Yes, if never approved |
| `CONTROLLED` | Approved and in force | No — new revision only |
| `OBSOLETE` | Withdrawn | No |

There is deliberately no fourth "REJECTED" status. A rejected document is one
that needs editing, and `UNDER PROCESS` already means exactly that; the rejection
is carried by `rejected_at` / `rejected_by` / `rejection_reason` and shown as a
banner. Adding a status that behaves identically to an existing one would put two
names on the same state.

Attachment changes require `status = 'UNDER PROCESS'` **and** `approval_date IS
NULL`. The second condition matters: a document that was approved once has a file
that is already part of a controlled record, whatever the document is doing now.

## 5. Approval

`approve_document` requires `documents.approve`, refuses anything not
`UNDER PROCESS`, refuses a document with no file attached, and in one transaction
sets `status = 'CONTROLLED'`, `approval_date = datetime('now')`,
`approved_by = <caller>`, clears the current rejection fields, and writes an
`APPROVED` activity row.

**The approval date is generated by the database.** It is not a parameter, and
never was accepted from the client after this stage.

### The bug this fixed

`create_document` and `update_document` took an `approval_date` argument and bound
it into the **`effective_date`** column:

```sql
INSERT INTO documents (..., effective_date, ...) VALUES (..., ?5, ...)
--                          ^^^^^^^^^^^^^^         ^^ approval_date
```

So the form's "Approval Date" was a free-text field that never touched
`documents.approval_date` — which is why an approved document displayed nothing.
The parameter is gone from both commands. Existing `effective_date` values are
untouched, and the UI still shows them for older records, marked as predating
approval tracking. A document that was already `CONTROLLED` before this workflow
existed reads **"Not recorded"** — it is not waiting for anything, and inventing a
date would be worse.

### Rejection

`reject_document` requires `documents.approve` and a non-whitespace reason,
records who and when, and keeps the document, its file and its revision history.
The document stays `UNDER PROCESS` so the author can correct and resubmit.

The five columns hold the **current** state; `activity_log` holds the **history**.
That is why approval clears the rejection fields without losing the rejection —
approving records an `APPROVED` row alongside the earlier `REJECTED` one.

## 6. Viewing

`Open` used to hand the file to Windows, which took a controlled record out of the
application entirely — past its permissions, into whatever the user's PDF
association is, and onto disk wherever that program caches it.

Now the bytes are fetched **by document id** over the existing IPC channel and
rendered to a canvas with pdfjs. No `file://` URL, no asset-protocol scope and no
custom URI scheme is opened, so no new surface exists through which the renderer
could name a different file. `documents.view` is checked on every read, so
guessing ids gains nothing.

Toolbar: page navigation, zoom in/out, fit width, print, close, open externally.
Non-PDF types are **not** embedded into the WebView — they show their metadata and
offer the external open.

pdfjs's standard font data is copied out of the installed package at
`prebuild`/`predev` (`scripts/copy-pdfjs-assets.mjs`) and served locally. Without
it, any document naming Helvetica or Times leaves `render()` waiting forever with
a blank page and nothing logged.

### Printing

`print_document_file` requires `documents.print` and invokes the Windows shell's
**print verb** on the backend-resolved file. The verb is fixed and the path is
never caller-supplied; both are passed as separate arguments rather than
interpolated into a command string. This is the OS print association, not a shell.

## 7. Permissions enforced

| Operation | Key |
|---|---|
| List / read / view bytes | `documents.view` |
| Create | `documents.create` |
| Edit metadata | `documents.edit` |
| Attach / replace / remove file | `documents.attachment_manage` |
| Approve / reject | `documents.approve` |
| Print | `documents.print` |
| Open outside the application | `documents.open_external` |

All seven already existed in the 53-key registry; none were added.

Opening externally moved from `documents.view` to `documents.open_external`. They
are not the same thing: viewing happens under the QMS's control, and opening
externally is the point past which the QMS can no longer say what happened to the
file.

### Who can approve — a distinction worth stating

Stage 4 was specified as "approval is an Admin function". Admin holds
`documents.approve`. **So does Quality Manager**, and that predates this stage:
migration 010 grants QualityManager every permission except `users.manage`,
`roles.manage`, `backup.create` and `backup.restore`, which sweeps
`documents.approve` in with the rest.

This has been left exactly as shipped. Narrowing it would revoke a capability from
every existing Quality Manager, change the 47-key count the Stage 2 tripwire
asserts, and make a privilege decision that belongs to the owner rather than to
the implementation of an approval screen. A test pins the real state so the
question stays visible. Auditor, Employee and Viewer hold no approval right.

Custom roles can also be granted `documents.approve` through the Roles &
Permissions editor — that is inherent to the RBAC architecture accepted in
Stage 2, not something introduced here.

## 8. Failure states

| State | Behaviour |
|---|---|
| Row exists, file missing | `get_document_file_info` reports `exists_on_disk: false`; the viewer explains and offers to re-attach if the document is still a draft. Nothing crashes. |
| Delete fails on disk | The transaction is not committed, so the record still truthfully says the file is attached. The database never claims a removal that did not happen. |
| File still referenced by another revision | Not deleted. The row is detached; the bytes stay. |
| File too large to preview | Refused above 100 MB with a clear message pointing at external open, rather than an opaque renderer failure. |
| Render stalls | After eight seconds the viewer says frames may not be arriving and points at external open. A silently blank page is the worst way to present a controlled document. |

## 9. Known remaining filesystem surface

Audited but **out of Stage 4 scope** — reported, not changed:

- **`restore_local_backup` / `create_local_backup`** accept a frontend-supplied
  absolute path with only `exists()` / `is_dir()` checks. Restore overwrites the
  live `data.db`, `settings.json` and the uploads tree. `backup.rs` already
  contains `validate_backup_path` and `validate_import_backup`, which implement
  the canonicalise-and-contain check — **and neither mutating command calls
  them**. Both also use `canonicalize(&p).unwrap_or_else(|_| p.clone())`, which
  falls back to the raw user string precisely when canonicalisation fails. This is
  the highest-value remaining hardening target.
- **The five other `open_*_attachment` commands** (CAPA, risks, complaints,
  audits, NC) resolve a DB filename with `exists()` only, without the
  canonicalise-and-contain check that documents now use. Not currently
  exploitable, because every writer generates the filename — but there is no
  defence in depth. `storage::resolve_managed_file` is ready to be applied to all
  five.
- **The five other `attach_*` commands** accept an import source path without
  `validate_import_source`.

None of these are regressions; all predate this stage.
